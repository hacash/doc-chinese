# 伊斯坦布尔升级技术说明书

 
本文以 `fullnodedev` 当前代码实现为主要依据，对“十一项关键能力”做白皮书风格的技术解释。面向技术调研、协议研究、钱包/网关开发、审计、安全分析与 DeFi 设计人员。 

---

## 摘要

伊斯坦布尔升级的核心，不是简单增加若干 action、opcode 或接口，而是把 Hacash 的可编程性从“单层逻辑”扩展为一套**分层可编程金融执行体系**：

- 在**交易层**显式表达执行边界、语义和流程；
- 在**结算层**统一处理多资产与多参与方清算；
- 在**资产层**把第三方资产纳入协议对象；
- 在**账户层**引入脚本账户与抽象账户入口；
- 在**执行层**用 HVM 承载复杂金融逻辑；
- 在**审计层**用 IR 反编译提高链上逻辑可读性；
- 在**资源层**用 protocol_cost、gas、状态租期约束长期资源消耗。

如果把比特币看作“可约束的价值转移系统”，把以太坊看作“通用合约状态机平台”，那么伊斯坦布尔升级后的 Hacash 更接近：

> **以交易、账户、资产、结算和合约共同组成的可编程金融执行系统。**

本文重点解释三类问题：

1. 这十一项能力在代码里分别是如何实现的；
2. 它们分别适用于哪些货币金融、资产流通和大规模 DeFi 场景；
3. 它们组合后，为什么会改变公链承载复杂金融业务的方式。

## 2. 术语表与对象模型

为了便于后文阅读，先统一几个关键术语。

### 2.1 交易对象

- **Type3 交易**：当前最重要的可编程交易类型，支持 AST、TEX、P2SH、合约调用等复杂执行路径。
- **Action**：交易中的最小动作单元。
- **Action Scope**：动作允许出现和执行的位置，例如 `TOP`、`AST`、`GUARD`、`CALL`。

### 2.2 账户对象

- **Privakey 地址**：普通私钥地址。
- **Contract 地址**：合约账户地址。
- **scriptmh 地址**：P2SH 风格脚本账户地址。

### 2.3 合约对象

- **HVM**：合约执行引擎。
- **IR / Bytecode**：HVM 支持的两类代码表示。
- **Abstract Call**：协议预定义的账户/生命周期钩子入口，例如 `PermitAsset`、`PayableHAC`、`Construct` 等。

### 2.4 结算对象

- **TEX Cell**：TEX 里的最小结算单元。
- **TEX Ledger**：交易内临时结算账本，用于零和检查和末尾结算。

### 2.5 意图与状态对象

- **Intent**：VM 内部、按合约所有权隔离的临时意图作用域与 KV 空间。
- **Active Storage**：活跃状态，可读可写。
- **Recoverable Storage**：恢复态状态，仍在链上但不能正常读写，只能续租、恢复或删除。
- **Absent Storage**：已彻底失效，视为不存在。

### 2.6 费用与资源对象

- **gas**：复杂执行路径消耗的协议资源计量。
- **protocol_cost**：针对长期资源占用或协议级对象扩张收取的协议费用。
- **storage rent / lease**：状态按区块推进持续消耗信用值的租期模型。

## 3. 为什么需要新的分层可编程性

### 3.1 传统脚本可编程性的边界

比特币路线证明了：链上价值转移不仅可以转移“钱”，也可以附带“花费条件”。  
P2SH、见证、脚本约束，使比特币非常适合：

- 支付；
- 冷热分层；
- 多签与托管；
- 条件解锁；
- 高确定性的保守资金控制。

但如果要表达：

- 多资产成交；
- 多步骤原子流程；
- 条件路由；
- 统一结算；
- 大规模金融状态机；

传统脚本体系通常不够自然。

### 3.2 通用合约可编程性的边界

以太坊路线证明了：把复杂逻辑交给通用 VM，可以极大释放协议创新能力。  
它适合：

- 快速试验新型协议；
- 构建任意业务状态机；
- DeFi lego 组合。

但其典型问题也很明显：

- 关键语义常常埋在合约内部；
- 交易外层不够可解释；
- 多资产结算多靠合约自管；
- 资产标准往往只是合约约定；
- 合约审计成本很高，很多风险隐藏在状态机细节里。

### 3.3 Hacash 的分层思路

伊斯坦布尔升级后的 Hacash，不完全沿用比特币或以太坊的单一路线，而是把不同问题分到不同层：

- **条件问题** 放到 Guard 层；
- **语义问题** 放到 Blob 层；
- **流程问题** 放到 AST 层；
- **清算问题** 放到 TEX 层；
- **资产问题** 放到协议资产层；
- **账户入口问题** 放到 P2SH / 抽象账户层；
- **复杂业务逻辑** 放到 HVM；
- **可读性与审计问题** 放到 IR 反编译层；
- **目标式执行协调** 放到 Intent；
- **长期资源边界** 放到租期与费用模型。

这种结构最重要的价值在于：

> **不是所有复杂性都必须被塞进一个黑盒合约。**

## 4. 与比特币、以太坊的可编程性对比

### 4.1 比特币：可约束的价值花费系统

比特币最擅长的是：

> “这笔价值能不能花、在什么条件下花。”

它的优势在于：

- 强约束；
- 强可验证；
- 规则边界清晰；
- 很适合托管、支付、保守型金融账户控制。

但它不天然擅长：

- 复杂链上流程编排；
- 多资产统一结算；
- 通用金融状态机；
- 高度语义化交易表达。

### 4.2 以太坊：通用合约状态机平台

以太坊最擅长的是：

> “让开发者用一台通用 VM 实现各种链上协议。”

它的优势在于：

- 表达力极强；
- 创新空间大；
- 标准化生态成熟；
- 合约组合灵活。

但它常见的问题是：

- 交易层语义较弱；
- 很多关键约束没有在外层显式化；
- 多资产清算往往要靠单个协议自己实现；
- 状态膨胀长期是结构性压力。

### 4.3 伊斯坦布尔升级后的 Hacash：分层可编程金融执行系统

伊斯坦布尔升级后的 Hacash 更强调：

- 交易语义显式化；
- 交易流程编排；
- 协议级结算；
- 协议级资产对象；
- 脚本账户与抽象账户并存；
- 合约逻辑可读可审计；
- 长期状态资源有租期边界。

### 4.4 对比表

| 维度 | 比特币 | 以太坊 | 伊斯坦布尔升级后的 Hacash |
|---|---|---|---|
| 可编程性的主要落点 | 花费条件 / 脚本 | 合约状态机 | 交易层 + 账户层 + 结算层 + 合约层 |
| 交易语义表达 | 弱 | 弱，常埋于 calldata / 合约 | 强，交易层可显式表达 |
| 多步骤流程编排 | 很弱 | 多由合约内部实现 | AST 原生支持 |
| 多资产统一结算 | 不自然 | 通常由合约维持内部账本 | TEX 协议级支持 |
| 第三方资产 | 原生较弱 | 多为合约标准 | HIP20 纳入协议级资产体系 |
| 账户可编程性 | 脚本账户 | 合约钱包 / AA 扩展 | P2SH + 协议级抽象账户钩子 |
| 合约可读性 | 不是重点 | 多依赖源码验证 | IR 可反编译与 sourcemap |
| 状态长期成本边界 | 无复杂合约存储问题 | 状态膨胀压力大 | 状态租期、恢复、删除边界更明确 |
| 更适合的场景 | 条件支付、托管 | 通用 dApp、快速试验 | 货币金融、资产流通、复杂清算、大规模 DeFi |

### 4.5 三条路线的结构示意图

```text
比特币路线
  交易
   ↓
  UTXO 选择
   ↓
  Script / P2SH 解锁验证
   ↓
  输入输出结算

以太坊路线
  交易
   ↓
  调用某个合约入口
   ↓
  合约内部状态机执行
   ↓
  日志 / 余额 / 存储变更

   ├─ Guard：先声明执行边界
   ├─ Blob：附带业务语义
   ├─ AST：选择执行路径
   ├─ TEX：统一多资产清算
   ├─ P2SH / 抽象账户：控制资金入口与出口
   └─ HVM：承载复杂金融逻辑
                ↓
        deferred / refund / fee 收尾
```

### 4.6 可编程性显式层级矩阵

| 关键能力 | 比特币主要落点 | 以太坊主要落点 | Hacash 主要落点 |
|---|---|---|---|
| 条件约束 | 脚本层 | 多在合约层 | 交易 Guard 层 + 账户层 |
| 业务语义 | 很弱 | 多在 calldata / 合约解释 | 交易 Blob 层 |
| 流程编排 | 很弱 | 多在合约内部 | 交易 AST 层 |
| 多资产结算 | 不自然 | 多在协议合约内部 | 协议 TEX 层 |
| 资产模型 | 原生弱，多靠外围协议 | 合约标准 | 协议资产层 + 合约钩子 |
| 账户规则 | 脚本条件 | 合约钱包 / AA | P2SH + 抽象账户 |
| 复杂金融逻辑 | 很受限 | 通用 VM | 金融导向 HVM |
| 可读审计 | 以脚本可读为主 | 常依赖源码验证 | IR 反编译 + sourcemap |
| 长期状态边界 | 无复杂合约存储租期 | 主要靠 gas / 设计自律 | 协议租期与 protocol_cost |

### 5.2 设计原则

伊斯坦布尔升级在代码实现上体现出五个明显设计原则：

1. **分层处理复杂性**：约束、流程、结算、账户、合约各司其职；
2. **尽量显式语义化**：关键条件和意图不必全部埋进黑盒合约；
3. **原子与回滚优先**：AST 和 TEX 都强调执行隔离与最终一致性；
4. **账户与资产协议化**：账户入口和资产对象被上提到协议层；
5. **资源长期可持续**：状态占用、部署扩张和复杂执行都需要定价。

## 6. 统一执行流程

这一节先不按能力拆分，而是从整体执行路径看系统是如何运转的。

### 6.1 Type3 交易主流程

```text
提交 Type3 交易
   ↓
交易拓扑/作用域预检查
   ↓
初始化 gas 预算
   ↓
顺序执行顶层 actions
   ↓
每个 action 经过统一包装：
  - 升级/门控检查
  - runtime scope 检查
  - 按 action 大小计算基础 gas
  - 执行业务逻辑
  - 触发 action hook
   ↓
全部 action 执行完毕后
   ↓
执行 TEX 统一结算
   ↓
执行 deferred phase
   ↓
成功路径上做 gas refund / 统计提交 / fee 扣减
```

其含义是：交易不是“动作一旦成功立即全部终结”，而是在顶层动作之后还存在：

- **统一结算阶段**；
- **延迟回调阶段**；
- **最终 gas 与 fee 收尾阶段**。

因此，交易在协议层已经具有多阶段提交的味道。

### 6.2 AST 子项执行流程

```text
进入 AST 子项
   ↓
创建局部快照（state / vm volatile / logs / tex）
   ↓
尝试执行子动作
   ├─ 成功 → 计费 → 提交该子快照
   ├─ Revert → 回滚该子快照，仅该分支失败
   └─ Fault  → 上抛，由更外层决定整体失败
```

这使 AST 可以做：

- fallback；
- 条件分支；
- 失败隔离；
- 部分成功选择。

### 6.3 转账钩子流程

```text
执行普通转账 action
   ↓
进入 do_action_hook
   ↓
判断 from / to 是否为特殊账户
   ├─ from 是 scriptmh → 调用 P2SH 入口校验脚本
   ├─ from 是合约     → 调用 Permit* 抽象入口
   └─ to   是合约     → 调用 Payable* 抽象入口
```

也就是说，普通资产转移并不是“只改余额”这么简单；它还能自然变成：

- 账户级策略校验；
- 接收侧自动记账；
- 支出侧自动授权；
- 脚本账户解锁执行。

### 6.4 TEX 统一结算流程

```text
执行每个 TEX cell
   ↓
局部更新状态 + 更新 TEX ledger
   ↓
交易末尾进入 do_settlement
   ↓
检查 HAC / SAT / HACD / Asset 是否净额归零
   ↓
对 diamond 池做 FIFO 分配
   ↓
完成最终物化转移
```

这说明 TEX 不是“动作列表”，而是“**交易内的统一清算账本**”。

## 8. ActionGuard

### 8.1 技术定位

ActionGuard 在代码里不是单独一个类，而是一类 **`ActScope::GUARD`** 动作。它们可出现在：

- 顶层交易；
- AST 分支；

但不能从 VM 的 `CALL` 执行上下文中任意触发。

### 8.2 当前实现的主要 Guard 动作

- `ChainAllow`：限制链 ID；
- `HeightScope`：限制区块高度窗口；
- `BalanceFloor`：限制某地址在当前执行点的最低余额；
- `TxMessage` / `TxBlob`：守卫层上的语义型动作。

### 8.3 执行机制

Guard action 在执行前后有两个关键检查：

1. **作用域检查**：只能在允许的位置执行；
2. **交易拓扑检查**：不允许整笔交易全是 Guard 而没有真正业务动作。

因此，Guard 的设计角色是：

> **声明执行边界，而不是替代业务动作本身。**

### 8.4 作用与意义

它让交易在进入真正资产流转、合约调用和结算之前，就能先表达：

- 时间条件；
- 链环境条件；
- 余额底线；
- 上下文说明。

这对金融系统意义很大，因为很多交易真正的风险并不在“怎么执行”，而在“**到底什么时候允许执行**”。

### 8.5 使用模板

```text
Guard 1: 限定链环境
Guard 2: 限定有效区块范围
Guard 3: 限定执行时最低余额
Action : 真正业务动作（转账 / TEX / 合约调用 / 路由）
```

### 8.6 典型场景

- 限价单与到期单；
- 大额资金划转的底仓保护；
- 防跨链回放；
- 面向机构账户的预风控交易。

### 8.7 金融例子

**条件换汇单**：

- 仅允许在主网执行；
- 仅在未来 20 分钟的链上区块窗口内有效；
- 成交后账户仍需保留最低保证金；
- 条件不满足则整个交易直接失效。

这类交易非常接近传统金融里“带有效期与风控边界的委托”。

## 9. TxBlob

### 9.1 技术定位

`TxBlob` 是一个执行时不修改状态、只携带二进制业务数据的守卫层动作。

### 9.2 执行机制

- 执行时通过统一 action wrapper；
- 做作用域/升级检查；
- 按序列化大小消耗 gas；
- 不做链上状态变更；
- 返回空结果。

### 9.3 作用与意义

TxBlob 的意义不在“执行逻辑”，而在：

> **把交易从纯状态变更记录，提升为带上下文的业务载体。**

它可用于承载：

- 订单摘要；
- 报价快照；
- 结算说明；
- 审计凭证 hash；
- 业务系统索引字段。

### 9.4 为什么重要

如果复杂金融交易只剩下“合约调用 + 原始字节”，那么钱包、浏览器、审计系统很难解释清楚业务含义。TxBlob 提供了一个协议层的语义承载位。

### 9.5 使用模板

```text
TxBlob(data = 订单参数/结算凭证/路由上下文)
+ Guard 约束
+ 真正转账/结算/合约动作
```

### 9.6 金融例子

**链下撮合、链上结算的场外大宗交易**：

链下已经完成价格协商，链上只负责交割。此时 TxBlob 可承载：

- 订单号；
- 报价时间；
- 双方撮合摘要；
- 清算批次号；
- 风险复核材料 hash。

这样链上不仅知道“发生了交割”，还知道“这次交割对应哪笔业务”。

## 10. AST

### 10.1 技术定位

AST 是交易级流程控制系统，是 Type3 交易最关键的结构能力之一。

当前核心节点：

- `AstSelect`：从一组动作中尝试执行若干个，满足最少成功数即可；
- `AstIf`：执行条件分支，根据条件成功与否选择 if / else 路径。

### 10.2 执行机制

AST 的关键不在“有 if/else 语法”，而在它的**隔离与回滚语义**：

- 每个子项都在局部快照中运行；
- 成功则提交该子快照；
- `Revert` 则仅回滚该子项；
- Fault 则上抛，由外层决定整体失败。

这说明 AST 的本质不是脚本语法糖，而是：

> **交易级分支与回滚控制系统。**

### 10.3 设计价值

AST 解决的问题不是“多写几步动作”，而是：

- 如何让一笔交易尝试多个路径；
- 如何让失败路径不污染成功路径；
- 如何让业务逻辑在交易层而不是合约内部具备流程感。

### 10.4 使用模板

#### 模板 A：路由选择

```text
AstSelect(min=1, max=1)
  ├─ 路径A
  ├─ 路径B
  └─ 路径C
```

含义：三条路径中成功一条即可。

#### 模板 B：条件执行

```text
AstIf(
  cond = 条件检查,
  br_if = 满足条件的执行路径,
  br_else = 不满足条件时的备选路径
)
```

### 10.5 典型场景

- 聚合路由；
- 条件成交；
- 自动 fallback；
- 清算失败切换路径；
- 组合策略择优执行。

### 10.6 金融例子

**多池最优路由**：

用户提交一笔兑换交易：

1. 优先尝试深度最大池；
2. 若因滑点失败，自动回退；
3. 再尝试次优池；
4. 若仍失败，走库存金库或挂单库存路由；
5. 至少成功一条才算本笔交易成功。

这是高级 DeFi 聚合器的核心能力之一，而 AST 把它直接提升到了交易层。

### 10.7 AST 决策树示意图

```text
                 [条件/目标]
                      │
                AstIf / AstSelect
            ┌─────────┼─────────┐
            │         │         │
          路径A     路径B     路径C
            │         │         │
         success   revert    success
            │         │         │
            └────┐    │    ┌────┘
                 │    │    │
                 └─ 选择成功路径 ─┘
                        │
                    进入后续结算
```

## 11. TEX

### 11.1 技术定位

TEX 是协议级原子结算层。  
它不是一个普通 action 列表，而是：

- 一套结算 cell 语言；
- 一个交易内临时净额账本；
- 一个交易末尾统一结算器。

### 11.2 核心对象

- `TexCellAct`：由参与者签名的 cell bundle；
- `TexLedger`：记录 HAC / SAT / HACD / Asset 的净额变化；
- `CellTrs*`：支付/获取 cell；
- `CellCond*`：条件 cell；
- `do_settlement`：末尾统一清算。

### 11.3 执行模型

TEX 的核心思想可以概括为：

> **先在交易里记账，后在交易末尾统一清算。**

具体流程：

1. 各参与者提交自己的 `TexCellAct`；
2. 每个 cell 执行时修改局部状态并更新 `TexLedger`；
3. 末尾统一检查各类资产净额是否归零；
4. 若不归零，则整笔交易失败；
5. 对于 diamond，使用共享池 + FIFO 名称分配进行最终物化结算。

### 11.4 一个重要实现特征：可重放签名片段

`TexCellAct` 的签名覆盖 `addr + cells`，而不覆盖交易哈希。  
这使 TEX bundle 非常适合：

- 链下撮合；
- 多方预签；
- 由聚合者在链上装配成交易；

但也意味着：

- 最好与 `HeightScope`、`ChainAllow`、TEX 条件 cell 等搭配使用；
- 以控制 bundle 的有效范围，避免无约束重放。

### 11.5 设计价值

TEX 把“清算一致性”从单个合约内部提升到协议层。  
对于多方成交和多资产互换，这非常关键，因为高级金融系统难点往往不是“动作很多”，而是：

- 谁付什么；
- 谁取什么；
- 中间失败会不会留脏状态；
- 最终是否配平；
- 是否可以一次完成统一清算。

### 11.6 使用模板

```text
参与者 A 的 TexCellAct:
  Pay Asset X
  Get HAC
  Cond Height <= deadline

参与者 B 的 TexCellAct:
  Pay HAC
  Get Asset X
  Cond ChainId == target

交易末尾:
  TEX ledger 检查净额是否全部归零
```

### 11.7 典型场景

- 订单簿撮合；
- 多资产原子交换；
- 多方净额清算；
- 金库份额赎回；
- 钻石池化交割。

### 11.8 金融例子

**订单簿撮合清算器**：

- A 支付稳定币，获得 HAC；
- B 支付 HAC，获得稳定币；
- 可能还有手续费收取方、做市库存方；
- 所有参与方各自签自己的 TEX bundle；
- 聚合者组装进同一笔交易；
- 末尾统一净额检查与结算。

这非常像链上的“小型清算所”。

### 11.9 TEX 结算账本示意图

```text
参与者A: Pay Asset X  ─────┐
                           │
参与者B: Pay HAC      ─────┼──> [TEX Ledger]
                           │        │
参与者C: Fee Receive  ─────┘        │
                                    │
                        检查净额是否全部归零
                                    │
                      归零 -> 统一物化结算
                      不归零 -> 整笔交易失败
```

## 12. HIP20（第三方资产发行）

### 12.1 技术定位

从代码实现看，HIP20 不是纯合约代币标准，而更接近：

> **协议级原生资产对象 + 合约级业务控制钩子。**

### 12.2 核心机制

#### 资产创建

- `AssetCreate` 创建资产元数据；
- 元数据包括 `issuer / serial / supply / decimal / ticket / name`；
- 协议检查 serial 窗口与 metadata 合法性；
- 收取 `protocol_cost`；
- 把全量初始 supply 记入 `issuer` 地址。

#### 资产转移

- `AssetToTrs`
- `AssetFromTrs`
- `AssetFromToTrs`

这些都是协议动作，不是用户自写合约余额表。

#### 与合约钩子联动

当资产从/向合约账户流动时，协议会自动触发：

- `PermitAsset`
- `PayableAsset`

### 12.3 与以太坊 ERC20 的关键差异

ERC20 的核心是“合约自己维护一张余额映射表”。  
HIP20 在当前实现里的核心更像：

- 资产对象由协议维护；
- 余额在协议统一状态里流转；
- 合约不一定负责“存资产账本”，而是负责“控制资产业务语义”。

这使资产层更容易与：

- TEX；
- Guard；
- 账户抽象；
- 协议统计与费用模型；

进行统一协同。

### 12.4 设计价值

HIP20 的意义不只是“能发一个 token”，而是：

> **让第三方资产进入协议原生资产体系，成为可被统一结算、统一守卫、统一账户控制的对象。**

### 12.5 使用模板

```text
1. AssetCreate 创建资产
2. issuer 获得初始 supply
3. 通过 Asset*Trs 进行协议级转移
4. 如资产进出合约账户，自动由 PermitAsset / PayableAsset 处理业务规则
```

### 12.6 典型场景

- 稳定币；
- 存款凭证；
- 金库份额；
- 商业积分；
- 票据；
- RWA 碎片化份额；
- 游戏/应用内资产。

### 12.7 金融例子

**HACD 碎片化资产（HACDS）**：

- 合约接收 HACD；
- 按规则映射为可分割资产份额 `HACDS`；
- 份额可继续流通、结算和二级交换；
- 未来可按规则赎回回 HACD。

这实际上已经体现出“底层稀缺资产 → 份额化金融资产”的标准范式。

## 13. HVM

### 13.1 技术定位

HVM 是 Hacash 的合约执行引擎，是承载复杂金融逻辑的核心运行时。

### 13.2 核心特征

- 支持 `IRNode` 与 `Bytecode` 双格式；
- 支持部署、升级、抽象入口、普通函数入口；
- 支持 `edit / view / pure` 模式；
- 支持状态存储、日志、上下文、延迟回调；
- 支持普通入口、P2SH 入口、abstract 入口三种执行入口。

### 13.3 执行模型

```text
入口调用（Main / Abst / P2sh）
   ↓
构造执行上下文与 frame bindings
   ↓
校验入参与效果模式
   ↓
解释执行 bytecode / 先由 IR 转 bytecode 再执行
   ↓
通过 host 访问状态、日志、存储、回调、链上上下文
   ↓
在边界处校验返回值
```

### 13.4 IR 与 Bytecode 的双格式意义

双格式意味着 HVM 同时兼顾两件事：

- **执行效率与验证**：运行时可统一落到 bytecode；
- **可读性与审计性**：部署与存储时可保留 IR 语义。

这在传统通用 VM 里并不常见。

### 13.5 设计价值

HVM 的价值不只是“支持合约”，而在于：

- 可被交易层、账户层、结算层组合使用；
- 与抽象账户、P2SH、Intent、状态租期天然衔接；
- 适合表达储备、份额、赎回、利率、期限、边界条件等金融逻辑。

### 13.6 使用模板

```text
编写 Fitsh / IR
   ↓
编译为 IR 或 bytecode
   ↓
ContractDeploy 部署
   ↓
通过 external function / abstract call / transfer hook 与外部交互
```

### 13.7 典型场景

- AMM；
- 金库策略；
- 借贷状态机；
- 份额计算；
- 稳定资产发行和赎回；
- 自动清算逻辑；
- 定时或延迟回调式资金处理。

### 13.8 金融例子

**AMM / LP 份额管理**：

测试代码里可以看到典型模式：

- 记录 total shares；
- 记录用户 LP 份额；
- 买卖前检查 deadline；
- 执行比例与份额计算；
- 在退出流动性时更新个人与全局状态。

这表明 HVM 已经能够直接承载典型 DeFi 状态机，而不是只适合轻量脚本。

### 13.9 HVM 在系统中的位置示意图

```text
交易 / 账户事件
      ↓
  普通入口 / 抽象入口 / P2SH 入口
      ↓
            HVM
      ↓      ↓      ↓
    存储    调用    回调
      ↓      ↓      ↓
   状态变更  子逻辑  defer
      ↓
  与 TEX / 账户钩子 / Intent 协同
```

## 14. P2SH

### 14.1 技术定位

当前实现中的 P2SH 更准确地说是 `scriptmh`：

> **Pay to Script-Merkle-Hash**

它不是“一个地址绑定一份脚本”，而是“一个地址绑定一组脚本叶子的 Merkle 根”。

### 14.2 核心机制

- 叶子承诺内容包括：`libs + codeconf + lockbox`；
- 分支哈希按固定规则计算；
- 最终根经 `ripemd160(root_sha3)` 生成 `scriptmh` 地址；
- 花费时用 `P2SHScriptProve` 提交 witness、脚本叶子、Merkle 路径；
- 协议把证明后的脚本对象放入当前交易上下文；
- 后续该地址发起转账时，自动执行 P2SH 入口验证。

### 14.3 设计价值

相较于传统单脚本哈希，`scriptmh` 的优势在于：

- 一个地址可承载多套策略；
- 不同风险等级的脚本路径可共存；
- 地址稳定，授权策略可分层组织；
- 很适合托管与金库系统。

### 14.4 使用模板

```text
1. 构造脚本叶子集合
2. 建 canonical Merkle tree
3. 得到 scriptmh 地址
4. 向该地址注资
5. 花费时提交 P2SHScriptProve + 真实转账动作
6. 协议自动在 action hook 中调用 P2SH 入口校验
```

### 14.5 典型场景

- 多策略资金金库；
- 托管账户；
- 多条件解锁；
- 分级审批支付；
- 多角色控制的业务账户。

### 14.6 金融例子

**机构金库**：

同一个 `scriptmh` 地址下有三类脚本：

- 日常支出脚本；
- 大额支付审批脚本；
- 紧急迁移/冻结脚本。

这样资金地址不需要变，权限结构却可以高度分层，极适合专业资金账户体系。

## 15. IR 反编译

### 15.1 技术定位

IR 反编译是“可审计层”的核心能力。  
它意味着链上逻辑不是只能以难读的低层表示存在，还可以还原到相对可读的源码形态。

### 15.2 核心机制

- `lang_to_irnode / lang_to_ircode`：源码 → IR；
- `ircode_to_lang / format_ircode_to_lang`：IR → 可读源码；
- `SourceMap` 恢复：
  - lib 名称；
  - 函数名称；
  - 参数名；
  - 局部变量名；
  - 常量名；
  - param prelude 结构。

### 15.3 设计价值

很多公链的已部署合约，一旦缺少源码验证，普通人几乎只能面对字节码黑盒。  
而 IR 反编译的价值在于：

- 降低审计门槛；
- 提高协议透明度；
- 让钱包/网关/治理工具能做更深入的逻辑可视化；
- 强化链上协议生态的公共可验证性。

### 15.4 使用模板

```text
部署侧保留 IR / sourcemap
   ↓
外部工具读取 IR code
   ↓
反编译为接近源码的结构化文本
   ↓
供审计、治理、钱包提示或风险分析使用
```

### 15.5 典型场景

- 审计 AMM 或金库策略；
- 比较升级前后合约逻辑差异；
- 钱包展示“将与哪类逻辑交互”；
- 安全准入、白名单与评分系统。

### 15.6 金融例子

**第三方钱包接入一个稳定资产金库**：

钱包不只是想知道“这个合约能调用”，而是想知道：

- 有无隐藏提款路径；
- 有无额外管理权限；
- 赎回逻辑是否透明；
- 升级授权是否合理。

IR 反编译使这种判断不再完全依赖项目方自述。

## 16. 账户抽象

### 16.1 技术定位

这里的账户抽象不是链外 bundler 模式，而是协议内建的**账户行为钩子机制**。

### 16.2 核心入口

- `PermitHAC / PermitSAT / PermitHACD / PermitAsset`：控制支出；
- `PayableHAC / PayableSAT / PayableHACD / PayableAsset`：控制接收；
- `Construct / Change / Append`：控制生命周期与升级。

### 16.3 执行机制

普通资产转账完成后，协议自动判断：

- 如果 `from` 是合约账户，调用 `Permit*`；
- 如果 `to` 是合约账户，调用 `Payable*`；
- 如果是部署或升级路径，则调用 `Construct / Change / Append`。

因此账户本身可以定义：

- 谁可以给我打钱；
- 我收到钱后要做什么；
- 我可以在什么条件下把钱转出去；
- 谁能改变我的逻辑与权限结构。

### 16.4 设计价值

账户抽象的本质是：

> **把账户从被动余额容器，升级为主动业务入口。**

这尤其适合金融场景，因为很多业务约束天然发生在“账户边界”而不是“合约函数调用”边界。

### 16.5 使用模板

```text
定义 abstract Payable*
  -> 控制接收语义
定义 abstract Permit*
  -> 控制支出语义
定义 abstract Construct/Change/Append
  -> 控制生命周期和升级权限
```

### 16.6 典型场景

- 智能金库；
- 受限收款账户；
- 自动记账账户；
- 合规资产账户；
- 链上企业财务账户。

### 16.7 金融例子

**受规则控制的稳定资产金库**：

- 只接受白名单清算合约转入某类资产；
- 只允许在赎回条件满足时支出储备资产；
- 每次收款自动记录内部账；
- 合约升级必须由治理合约授予。

这是一种“账户即规则入口”的金融账户模型。

## 17. Intent（意图）

### 17.1 技术定位

Intent 是 HVM 内部的、按合约所有权隔离的、可绑定作用域的临时协同空间。  
它不是永久存储，而是执行期的“目标上下文容器”。

### 17.2 核心机制

- `intent_new`：创建 intent；
- `intent_use`：绑定当前执行作用域；
- `intent_put / get / take / del`：读写中间状态；
- `intent_require*`：做中间约束验证；
- `defer`：注册延迟回调，可显式绑定或不绑定 intent scope。

### 17.3 一个关键语义

Intent 不是“全局共享 KV”，而是：

- 有 owner；
- 有 scope；
- 有调用链传播规则；
- 其他合约即使拿到 handle，也不能越权读写别人的 intent 数据。

### 17.4 设计价值

复杂金融业务中经常有大量“执行期中间态”：

- 目标资产；
- 路由阶段；
- 临时结果；
- 滑点阈值；
- 清算标记；
- 回调凭证。

如果这些全写入永久状态，会造成：

- 成本高；
- 易污染长期状态；
- 审计边界变复杂。

Intent 的价值就在于：

> **把临时目标和中间约束留在执行期，而不是永久链上状态。**

### 17.5 使用模板

```text
intent_new(kind)
  ↓
intent_use(handle)
  ↓
intent_put(key, value)
  ↓
跨合约调用时自动继承 scope
  ↓
defer / require / final check
```

### 17.6 典型场景

- 聚合器多跳换汇；
- 多步骤清算；
- 回调式资金分配；
- 策略执行阶段协调；
- 临时交易目标绑定。

### 17.7 金融例子

**多池路由器**：

聚合器创建一个 intent，并写入：

- 目标资产；
- 最低到手量；
- 当前尝试路径；
- 中间换算结果；
- 最后回调要验证的条件。

然后多个池子与金库都围绕同一 intent 执行。最后再统一确认目标是否达成。这非常接近“围绕业务目标组织执行”，而不是机械地把步骤一条条堆起来。

## 18. 合约状态租期

### 18.1 技术定位

合约状态租期是伊斯坦布尔升级最容易被低估、但长期意义极强的能力之一。  
它解决的是：

> **链上长期状态不能无限免费增长。**

### 18.2 核心对象

每个存储值 `ValueSto` 包含：

- `charge`：上次结算高度；
- `live_credit`：活跃期信用；
- `recover_credit`：恢复期信用；
- `data`：实际值。

### 18.3 状态生命周期

```text
新建状态
   ↓
Active（可读、可写）
   ↓ live_credit 持续消耗
Recoverable（仍在链上，但不能正常读写）
   ↓ recover_credit 持续消耗
Absent（彻底视为不存在）
```

### 18.4 支持的操作

- `storage_new`：新建并附带初始活跃租期；
- `storage_edit`：仅允许对 active 状态编辑；
- `storage_rent`：延长活跃期；
- `storage_recv`：延长恢复期；
- `storage_del`：删除并退回部分剩余信用；
- `storage_stat`：查看活跃/恢复剩余块数。

### 18.5 设计价值

状态租期的意义不只是“多一笔费用”，而是制度层面的：

- 长期状态有真实价格；
- 暂时不用的状态可以进入恢复期；
- 永久无人维护的状态最终退出活跃空间；
- 协议可持续性更强；
- 大规模 DeFi 的状态膨胀问题有明确治理边界。

### 18.6 使用模板

```text
storage_new(key, value, initial_period)
   ↓
正常使用时定期 storage_rent
   ↓
若已到恢复态，可 storage_recv
   ↓
不再需要则 storage_del
```

### 18.7 典型场景

- LP 仓位；
- 用户余额；
- 凭证状态；
- 存款记录；
- 长期订单；
- 票据生命周期管理。

### 18.8 金融例子

**大规模 LP 账户系统**：

一个 DeFi 协议可能有数百万个 LP 账户和碎片化头寸。租期模型允许协议区分：

- 高活跃用户的状态；
- 暂停使用但未来可恢复的状态；
- 长期无人维护应退出活跃空间的状态。

这使系统不至于因为历史碎片状态无限堆积而不可持续。

## 19. 资源边界与经济约束

虽然不属于“十一项能力”中的单独条目，但理解伊斯坦布尔升级必须同时理解两件事：

- **protocol_cost**
- **gas**

因为这些能力只有在明确的资源边界下才可长期运行。

### 19.1 protocol_cost 的角色

从当前代码实现看，protocol_cost 主要出现在：

- `AssetCreate`：资产发行；
- `ContractDeploy`：合约部署；
- `ContractUpdate`：合约扩容或编辑。

这意味着 protocol_cost 的本质不是“功能税”，而是：

> **对长期协议资源占用进行定价。**

尤其是：

- 新资产进入协议对象空间；
- 新合约进入长期链上状态；
- 合约字节与结构扩张；

都需要支付明确成本。

### 19.2 gas 的角色

gas 在 Type3 交易与 HVM 执行中承担的是：

- 复杂执行路径的资源边界；
- 交易编排与 VM 运行的消耗约束；
- AST 快照尝试成本；
- 返回路径与扩展动作的差额计费。

gas 的价值不是“奖励执行者的小费”这么简单，而更像：

> **限制复杂执行、为系统长期可持续保留资源边界的协议成本机制。**

### 19.3 为什么金融系统尤其需要它们

高级 DeFi 不是只靠“更多代码”实现的，而是需要同时解决：

- 长期状态如何定价；
- 多步骤执行如何定价；
- 多资产结算如何约束；
- 合约升级如何计价；
- 协议对象扩张如何有边界。

伊斯坦布尔升级的真正成熟之处，就在于它没有只谈表达力，而是同步为表达力加上了经济边界。

## 21. 对技术调研与安全审计的启示

从安全和研究角度看，伊斯坦布尔升级最值得关注的，不是“功能点变多”，而是**风险面发生了结构性变化**。

### 21.1 风险不再只在合约内部

风险现在可能分布在：

- Guard 条件是否充分；
- AST 回滚边界是否正确；
- TEX 配平是否严格；
- 账户钩子是否允许异常路径；
- P2SH 解锁脚本是否过宽；
- Intent 跨调用作用域是否正确；
- 状态租期是否导致边界状态误用。

### 21.2 审计对象从“单合约”扩展为“执行体系”

对研究人员而言，要看的不只是合约字节码，还包括：

- 交易层表达；
- 账户入口控制；
- 统一结算语义；
- 延迟回调与意图绑定；
- 长期资源和状态生命周期。

### 21.3 审计透明度也明显提升

同时，IR 反编译、显式 Guard、协议级资产对象和统一结算层，又在帮助审计从黑盒走向更可读、更结构化的分析对象。

换句话说，这次升级既增加了系统能力，也提高了系统被正确审视的可能性。

## 附录 B：案例化理解——这些能力如何落地

这一附录不再按功能模块拆解，而是按外部读者最容易理解的业务场景来解释：

- 如果要做链上订单簿与 RFQ 撮合，需要哪些能力协同；
- 如果要做底层资产份额化与储备金库，需要哪些能力协同；
- 如果要做大规模 DeFi 路由与统一清算，需要哪些能力协同。

其目的不是重复正文，而是回答更直接的问题：

> **使用这些能力，链上到底能具体做成什么系统？**

---

### B.1 案例一：链上 RFQ / 订单簿撮合系统

#### B.1.1 问题背景

传统订单簿或 RFQ 系统的关键难点，不只是“有人买、有人卖”，而是：

- 订单有没有有效期；
- 是否只在指定链环境下有效；
- 成交前账户是否仍满足库存或保证金要求；
- 如果主路径成交失败，是否可以切换到备选路径；
- 多方资产交换后，是否可以一次性完成清算；
- 钱包和审计系统是否看得懂这笔交易到底在做什么。

如果只有传统脚本能力，通常只能表达局部花费条件。  
如果只有通用合约能力，则往往要把大量订单约束、撮合上下文和结算逻辑一起塞进一个合约状态机中。

伊斯坦布尔升级后的 Hacash，则可以把这些问题拆到不同层解决。

#### B.1.2 能力组合

这个场景通常会同时使用：

- **ActionGuard**：限制时间窗、链环境、底仓条件；
- **TxBlob**：携带订单参数、报价摘要、批次号；
- **AST**：尝试不同成交路径并在失败时回退；
- **TEX**：把最终多方成交统一结算；
- **HIP20**：让稳定币、票据类资产、份额资产进入协议级交割层；
- **账户抽象**：让金库账户、做市库存账户、清算账户自动做入账/出账规则校验。

#### B.1.3 一个典型执行流程

```text
用户提交一笔 Type3 交易
  ↓
Guard 声明：
  - 只允许在目标链执行
  - 只允许在截止高度前执行
  - 执行后账户仍需满足最低余额/库存
  ↓
TxBlob 携带：
  - 订单编号
  - 报价摘要
  - RFQ 结果摘要
  - 风控校验凭证 hash
  ↓
AST 尝试成交路径：
  - 路径A：优先成交池
  - 路径B：备选库存池
  - 路径C：做市商库存路径
  ↓
成功路径进入 TEX
  ↓
TEX 统一检查多方资产净额是否归零
  ↓
清算完成
```

#### B.1.4 为什么这比传统交易调用更强

因为它把订单系统最关键的几个维度都协议化了：

- **前置约束** 不必全部埋在合约内部；
- **业务语义** 不必丢失在原始 calldata 中；
- **失败回退** 不必由一个庞大合约手写控制流来承担；
- **统一清算** 不必由单个撮合合约自管全部配平逻辑；
- **账户权限** 不必全部退化成“谁能签名谁就能动钱”。

#### B.1.5 这类系统能发展成什么

如果进一步叠加：

- 做市商库存账户；
- 受控清算金库；
- 多种 HIP20 资产；
- 延迟回调型风控确认；

那么 Hacash 可以自然承载：

- 限价单；
- RFQ 成交；
- 场外大宗结算；
- 多资产订单簿；
- 更接近传统交易场所的链上清算流程。

#### B.1.6 与比特币 / 以太坊路线的直观区别

- 在比特币风格系统里，做“条件花费”很自然，但做“多方、多资产、带回退路径的成交清算”不自然；
- 在以太坊风格系统里，能做复杂撮合合约，但很多语义和结算约束都藏在合约里；
- 在 Hacash 这里，**订单条件、交易语义、流程编排和最终清算可以分层表达**。

这会显著提高：

- 钱包展示能力；
- 风险系统的可读性；
- 协议的可审计性；
- 对接传统金融业务规则的能力。

### B.2 案例二：HACD / RWA / 储备资产的份额化与金库流通系统

#### B.2.1 问题背景

很多资产天然不适合直接高频流通，例如：

- HACD 这类稀缺资产；
- 实物资产或票据；
- 长期储备资产；
- RWA 类凭证；
- 大额金库头寸。

这类资产如果要进入更活跃的链上市场，通常需要完成：

1. 托管；
2. 份额化；
3. 凭证发行；
4. 二级流通；
5. 可验证赎回。

#### B.2.2 能力组合

这个场景通常会同时使用：

- **HIP20**：发行协议级份额资产；
- **HVM**：实现入库、映射、赎回、费率、份额和限制逻辑；
- **P2SH**：把底层储备资产放进脚本控制金库；
- **账户抽象**：定义接收底层资产和放出底层资产的条件；
- **IR 反编译**：让外部观察者可审计份额化逻辑；
- **状态租期**：让大规模持有人状态、金库份额状态有长期成本边界。

#### B.2.3 一个典型执行流程

```text
用户把底层资产存入金库账户
  ↓
金库账户通过 Payable* 入口校验入库合法性
  ↓
HVM 根据规则计算应铸出的份额数量
  ↓
协议级资产（HIP20）发放到用户账户
  ↓
用户可像普通协议资产一样转移、结算、参与二级流通
  ↓
未来用户提交赎回交易
  ↓
Permit* / 金库逻辑校验赎回条件
  ↓
放出底层资产并销毁或回收份额资产
```

#### B.2.4 为什么这个模型重要

因为它把“储备 → 份额 → 流通 → 赎回”的链条做成了统一协议结构，而不是完全依赖一个自定义代币合约和若干外围脚本。

其中最关键的价值有四个：

1. **底层资产可托管**：P2SH 和账户抽象可以让托管规则明确化；
2. **份额资产可流通**：HIP20 使份额直接进入协议资产体系；
3. **逻辑可审计**：HVM + IR 反编译提升透明度；
4. **资源可持续**：大量份额账户和金库状态不会无限免费增长。

#### B.2.5 HACD 视角下的直观理解

以 HACD 为例，可以很容易理解这个模型的意义：

- HACD 本身适合被看作高价值、低频、稀缺资产；
- 但市场可能需要更细粒度、更高频、更可组合的流通单位；
- 那么就可以通过合约把 HACD 映射为可分割的份额资产；
- 这些份额资产再被用于：
  - 二级流通；
  - 抵押；
  - 组合支付；
  - 流动性池；
  - 金库凭证。

这实际上就是“**底层价值储备资产的金融化**”。

#### B.2.6 更大尺度的延伸：RWA 与储备凭证

同样的结构还可以进一步扩展到：

- 贵金属凭证；
- 仓单；
- 票据；
- 国债型凭证；
- 稳定资产准备金凭证。

在这种情况下，Hacash 的意义就不只是“发一个 token”，而是：

> **把储备资产、凭证资产和赎回规则一起做成可编程、可审计、可结算的统一协议结构。**

#### B.2.7 与传统公链做法的区别

- 在很多传统公链里，份额资产常常只是某个合约自己的内部 token；
- 在 Hacash 这里，份额资产可以进入协议资产层，并与 TEX、Guard、抽象账户、统一转账钩子协同；
- 这意味着份额资产更容易被纳入统一结算和统一金融流程，而不是长期困在某个孤立合约系统里。

### B.3 案例三：大规模 DeFi 路由、组合执行与统一清算系统

#### B.3.1 问题背景

高级 DeFi 的难点，从来不是“写一个合约”本身，而是：

- 多池流动性如何择优使用；
- 多步骤操作如何原子执行；
- 失败的中间步骤如何不污染最终状态；
- 多资产路径最后如何统一清算；
- 数百万用户和大量头寸状态如何长期可持续。

如果这些问题全部压给单个通用合约处理，系统常常会变得：

- 状态过重；
- 路径过深；
- 审计边界过于复杂；
- 资源成本不透明。

#### B.3.2 能力组合

这个场景通常会同时使用：

- **HVM**：承载池子逻辑、份额逻辑、报价逻辑、清算逻辑；
- **Intent**：承载执行期的目标和中间上下文；
- **AST**：实现条件分支、fallback 和路径选择；
- **TEX**：在最后统一做净额结算；
- **Guard**：限定时间窗、链环境和最小结果条件；
- **状态租期**：约束长期状态增长。

#### B.3.3 一个典型执行流程

```text
用户提交一笔复杂 DeFi 交易
  ↓
Guard 声明：
  - 截止高度
  - 目标链环境
  - 最低到账条件 / 最低保证金条件
  ↓
TxBlob 附带路由摘要 / 风控上下文
  ↓
HVM Router 创建 intent
  ↓
intent 中记录：
  - 目标资产
  - 最小到手量
  - 当前路径编号
  - 中间资金状态
  - 最终校验条件
  ↓
AST 按顺序尝试不同路径
  - 池A
  - 池B
  - 金库库存
  - 组合清算路径
  ↓
各路径中的资产流和账务进入 TEX ledger
  ↓
交易末尾统一净额结算
  ↓
defer / final check 校验目标是否完成
```

#### B.3.4 为什么 Intent 在这个场景特别重要

在复杂路由中，常常会出现大量中间信息：

- 当前尝试哪条路径；
- 前一步输出了多少资产；
- 还剩多少资金待处理；
- 是否满足某个阶段性条件；
- 最终要验证什么目标。

如果这些全写进永久 storage：

- 成本高；
- 污染长期状态；
- 审计边界恶化；
- 容易留下历史垃圾。

Intent 让这些数据存在于**执行期间**，这对高频复杂 DeFi 至关重要。

#### B.3.5 为什么 TEX 在这个场景特别重要

即使某条路径在逻辑上成立，最终还要解决一个根本问题：

> **整笔交易涉及的多种资产，最后有没有真正完成统一清算？**

TEX 在这里扮演的不是“某个 swap 动作”，而是：

- 多方路径收束点；
- 多资产账务配平器；
- 交易级清算器。

这使大型 DeFi 系统更容易从“多个合约局部正确”走向“整笔业务全局一致”。

#### B.3.6 为什么状态租期在大规模 DeFi 中不可忽略

假设未来出现：

- 数百万用户；
- 大量小额仓位；
- 大量 LP 份额；
- 大量已经长期不用的历史状态；

那么如果没有租期和恢复边界，协议很容易面临状态无限膨胀的问题。

状态租期在大规模 DeFi 中的意义，不只是收费，而是：

- 把“谁为长期状态负责”制度化；
- 把“什么状态应该继续留在活跃空间里”制度化；
- 把“协议是否能长期承载海量金融对象”制度化。

#### B.3.7 最终能演化成什么系统

当上述能力成熟叠加后，Hacash 可以自然支撑：

- 路由器；
- 多池聚合器；
- 清算器；
- 多资产支付网络；
- 自动化策略执行系统；
- 组合型 DeFi 工作流引擎；
- 更贴近真实金融业务链条的链上执行系统。

换句话说，这不是“多几个 swap 合约”的升级，而是：

> **为复杂金融系统提供了交易层、账户层、结算层和执行层同时可编程的基础。**

### B.4 三个案例的统一结论

如果把前面三个案例放在一起看，会发现伊斯坦布尔升级后的 Hacash 并不是单点增强，而是在建立一种新的系统能力：

#### B.4.1 交易不再只是转账容器

交易开始可以表达：

- 条件；
- 语义；
- 路径；
- 清算；
- 上下文。

这意味着交易越来越像“业务单元”，而不是纯粹的状态修改请求。

#### B.4.2 账户不再只是签名主体

账户开始可以表达：

- 收款规则；
- 出款规则；
- 脚本约束；
- 升级权限；
- 业务入口语义。

这意味着账户越来越像“策略入口”，而不是纯粹的余额容器。

#### B.4.3 资产不再只是合约内部映射表

资产开始可以：

- 成为协议级对象；
- 被统一转移；
- 被统一结算；
- 被统一守卫；
- 被统一接入账户抽象和脚本账户控制。

这意味着资产越来越像“统一金融对象”，而不是孤立 token 合约里的局部变量。

#### B.4.4 公链开始更适合承载真实金融业务链条

真实金融业务通常不是单一步骤，而是：

- 先检查条件；
- 再附带业务上下文；
- 然后执行若干步骤；
- 中间可能回退或改道；
- 最后统一结算；
- 并且要考虑长期状态成本。

伊斯坦布尔升级最重要的意义，就是让 Hacash 开始具备这种完整链条的原生表达能力。

### B.5 给读者的一句话

如果只用最外部、最直观的话来理解这些能力，那么可以这样总结：

- **比特币**告诉我们：链上价值可以带条件地安全花费；
- **以太坊**告诉我们：链上协议可以在通用 VM 中自由生长；
- **伊斯坦布尔升级后的 Hacash**则在尝试把两者再往前推进一步：

> **让交易、账户、资产、结算和合约共同构成一个更适合货币金融、资产流通和大规模 DeFi 的开放执行系统。**

这也是为什么这次升级真正值得技术调研人员重视：  
它并不是在回答“链上还能多做什么小功能”，而是在回答：

> **公链究竟应当如何原生承载更复杂、更可审计、更可持续的金融业务。**
