# Hacash 多层可编程性架构

---

## 摘要

Hacash 采用了一种独特的"分层递进"可编程性架构，从最底层的原子化资产操作（Layer 1）到完整的图灵完备合约（Layer 6），每一层在前一层基础上扩展能力，同时保持向下兼容。其中 Layer 5 的 IR 反编译能力使得链上合约字节码可被完整还原为 fitsh 源码，赋予合约"原生可审计性"——这在大额金融结算和机构级 DeFi 场景中具有独特价值。本报告从大额金融结算和 DeFi 公链的视角，对该架构进行客观的技术评估。

---

## 1. 架构总览

```
Layer 6 ─ 合约状态读写、自定义资产、任意 DeFi
Layer 5 ─ IR 反编译与双格式虚拟机代码（fitsh ↔ bytecode）
Layer 4 ─ 账户抽象（AbstCall）、P2SH 脚本账户
Layer 3 ─ 交易内嵌脚本执行（MainCall + EXTACTION）
Layer 2 ─ AST 条件逻辑（AstSelect / AstIf）
Layer 1 ─ 原子化 Action 组合（AND 语义事务）
```

每笔交易（tx）包含一个有序的 action 列表。所有 action 必须全部成功，否则整笔交易回滚。这是最基础的事务保证。

---

## 2. 各层详细分析

### 2.1 Layer 1：原子化 Action 组合

**机制**：交易包含 `Vec<Box<dyn Action>>`，按序执行，任一失败则整笔 tx 回滚。每个 action 是一个类型化的结构体（如 `HacToTrs`、`SatFromTrs`、`DiaFromToTrs`），对应一种确定性的资产操作。

**优点**：
- 声明式语义：转账意图在交易体中完全可见，无需执行即可审计。矿工、钱包、浏览器可以直接解析 action 列表得知资产流向，这对大额结算的透明性至关重要。
- 原生多资产：HAC、SAT（比特币单向转移）、HACD（钻石 NFT）、自定义 Asset 在协议层有独立的 action 类型，而非通过合约 token 标准实现。这消除了 ERC-20 类标准中常见的 approve/transferFrom 双步骤攻击面。
- 确定性 gas：每个 action 的 gas 消耗等于其序列化大小（`self.size() as u32`），可在提交前精确计算。
- 多方签名天然支持：`AddrOrList` 允许交易携带多个地址和对应签名，`req_sign()` 收集所有 action 需要的签名地址。多方原子交换不需要额外的合约逻辑。

**局限**：
- action 类型是协议硬编码的，新增资产操作类型需要硬分叉。
- AND 语义意味着无法表达"尝试 A，失败则做 B"的逻辑——这正是 Layer 2 解决的问题。

**与同类对比**：Bitcoin 的 UTXO 脚本也是声明式的，但缺乏多资产原生支持和多 action 组合。Ethereum 的交易只能调用一个入口点，多步操作必须通过合约编排。Hacash 的 Layer 1 在声明式可审计性和多资产原子操作方面具有结构性优势。

**实际场景**：一笔 5000 万美元的跨境贸易结算，买方支付 HAC、卖方交付 HACD 资产凭证、担保方释放保证金——三步操作通过 Layer 1 的多 action AND 组合在单笔 tx 内原子完成，任一步失败则全部回滚。全程逻辑在交易体中完全可见，矿工和审计方无需执行即可验证资产流向。

### 2.2 Layer 2：AST 条件逻辑

**机制**：`AstSelect` 和 `AstIf` 是特殊的 action 类型，可以嵌套包含其他 action，形成抽象语法树。

- `AstSelect(min, max, actions[])`：依次尝试执行每个子 action，成功的保留（merge），失败的回滚（recover），最终检查成功数量是否在 `[min, max]` 范围内。
- `AstIf(cond, br_if, br_else)`：执行 cond，成功则 merge cond 状态并执行 br_if，失败则 recover cond 状态并执行 br_else。

**状态隔离机制**：每次尝试执行前调用 `ctx_snapshot()` 捕获完整快照（state fork、VM volatile、logs、ctx volatile），失败时 `ctx_recover()` 完整回滚。Gas 消耗是单调的——失败分支消耗的 gas 不退还，防止免费试探攻击。

**深度限制**：AST 嵌套深度上限为 6 层（`AST_TREE_DEPTH_MAX`），通过 `AstLevelGuard` RAII 守卫保证 level 计数的正确恢复。

**优点**：
- 在不引入图灵完备脚本的前提下实现了条件逻辑，保持了 Layer 1 的声明式可审计性。交易体中的 AST 结构可以被静态分析——所有可能的执行路径和涉及的资产操作在提交前完全可见。
- 对大额金融结算场景极有价值：可以构造"如果条件 A 满足则执行方案 X，否则执行方案 Y"的原子交易，而无需信任任何合约代码。
- `collect_req_sign()` 递归收集所有分支中的签名需求，确保无论走哪条路径，所需签名都已提供。

**局限**：
- 条件判断的表达力有限——cond 分支的"成功/失败"是唯一的判断依据，无法基于返回值做更细粒度的分支。
- 嵌套深度 6 层对于复杂的多方协商场景可能不够。但考虑到这是链上共识层的限制，6 层已经足够覆盖绝大多数实际场景。

**与同类对比**：这是 Hacash 最独特的设计之一。Bitcoin 的 Script 没有条件 action 组合能力。Ethereum 没有交易级别的条件分支（必须通过合约实现）。最接近的类比是 Cosmos SDK 的 `MsgMultiSend`，但后者不支持条件逻辑。

**实际场景**：机构间隔夜拆借——通过 AstIf 构造"若抵押率达标则放款并锁定抵押品，否则退回本金"的原子交易。整个条件判断和资产操作在交易体中静态可见，无需信任任何合约代码。对于大额资金的条件支付，这种"无合约条件结算"能力消除了智能合约漏洞风险，同时保持了完整的可审计性。

### 2.3 Layer 3：交易内嵌脚本执行

**机制**：`TransactionType3` 引入了 `gas_max` 字段，允许交易携带 VM 可执行的脚本代码。通过 `setup_vm_run()` 进入 VM 执行，VM 内部可以通过 `EXTACTION` 指令回调 protocol 层的 action 系统。

**执行流程**：
1. `do_tx_execute()` 在执行 action 前调用 `do_vm_init()` 预初始化 VM
2. MainCall action 通过 `setup_vm_run(ctx, Main, ...)` 进入 VM
3. VM 执行脚本，遇到 `EXTACTION` 时通过 `host.ext_action_call()` → `ctx.action_call()` → `ctx_action_call()` 回到 protocol 层创建并执行 action
4. `ctx_action_call()` 统一处理 burn_90 gas 乘数和签名验证

**EXTACTION 安全限制**：
- 仅 `Main` 模式、`depth == 0`、非 `callcode` 上下文允许 EXTACTION
- 合约调用（Abst/Outer/Inner）和嵌套调用中禁止 EXTACTION
- 这确保了资产转移操作只能由交易发起者的顶层脚本触发

**Gas 模型**：
- `GasCounter` 管理整个 tx 的 gas 预算，所有 VM 调用共享同一个计数器
- 每种调用类型有最低 gas 消耗（`main_call_min`、`abst_call_min`、`p2sh_call_min`）
- 重入深度限制（`max_reentry_depth = 4`）通过 `GasCallGuard` RAII 守卫管理
- Gas 结算（HAC 燃烧）仅在最外层调用返回时执行一次

**优点**：
- 脚本可以编排复杂的多步操作，同时通过 EXTACTION 复用 Layer 1 的原子化资产操作，避免了在脚本层重新实现转账逻辑。
- EXTACTION 的严格限制防止了合约代码直接发起资产转移，这是对 Ethereum 中合约可以任意调用 `transfer()` 的一个重要安全改进。
- 共享 gas 计数器和重入深度限制提供了可预测的资源消耗上界。

**局限**：
- EXTACTION 仅限顶层 Main 调用，合约间无法通过 EXTACTION 互相转移资产——必须通过 AbstCall hook 机制。这增加了合约间交互的复杂度。
- 脚本语言（fitsh）是 Hacash 自定义的，生态工具链和开发者社区需要从零建设。

### 2.4 Layer 4：账户抽象与 P2SH

**机制**：Hacash 的地址系统区分三种类型：
- `privakey`：传统私钥地址
- `contract`：合约地址（由部署者地址 + nonce 计算）
- `scriptmh`：脚本哈希地址（P2SH）

当 Layer 1 的资产转移 action 涉及合约地址或脚本哈希地址时，`action_hook` 系统自动触发相应的 VM 调用：

**AbstCall（合约账户抽象）**：
- `PermitHAC/SAT/HACD/Asset`：从合约地址转出资产时触发，合约可以验证和授权
- `PayableHAC/SAT/HACD/Asset`：向合约地址转入资产时触发，合约可以执行接收逻辑
- `Construct`：合约部署时的构造函数
- `Change`/`Append`：合约升级

**P2SH（脚本哈希账户）**：
- 地址由脚本哈希生成，转出时需要提供原始脚本和 witness 数据
- 脚本在 VM 中执行，验证转账是否被授权

**优点**：
- 账户抽象是协议原生的，不需要像 ERC-4337 那样通过额外的基础设施层实现。每个合约地址天然具备 Permit/Payable 钩子能力。
- P2SH 提供了灵活的自定义签名验证，支持多签、时间锁、条件支付等场景，且不需要部署合约。
- hook 机制的设计使得 Layer 1 的资产操作和 Layer 4 的账户逻辑解耦——action 本身不知道目标地址是否是合约，hook 系统透明地处理。

**局限**：
- AbstCall 的类型是硬编码的枚举（Construct、Change、Permit*、Payable*），新增抽象调用类型需要协议升级。
- P2SH 脚本在每次转账时都需要提供完整代码（不像合约那样持久化存储），增加了交易体积。

**与同类对比**：Ethereum 的 ERC-4337 账户抽象需要 EntryPoint 合约、Bundler、Paymaster 等复杂基础设施。Hacash 的方案更简洁——合约地址天然具备账户抽象能力，无需额外部署。但 ERC-4337 的灵活性更高（自定义验证逻辑不受枚举类型限制）。

### 2.5 Layer 5：IR 反编译与双格式虚拟机代码

**机制**：Hacash VM 的合约代码体系支持两种等价表示格式：fitsh 高级语言和 bytecode 字节码。编译管线为 fitsh → IR（中间表示）→ bytecode，且该管线支持完整反向：bytecode → IR → fitsh。

**IR 层设计**：
- IR 定义了 IRLIST（0xF1）、IRBLOCK（0xF2）、IRBLOCKR（0xF3）、IRIF（0xF4）、IRIFR（0xF5）、IRWHILE（0xF6）等容器节点，精确控制栈纪律与求值顺序
- 每个 IR 节点通过 `hasretval()` 标记是否产生返回值，编译器据此自动插入 POP 指令维护栈平衡
- IR 节点可序列化/反序列化，保证 roundtrip 稳定性

**反编译能力**：
- `formater.rs` + `decompilation_helper.rs` 可将链上部署的原始字节码完整还原为可读的 fitsh 源码
- 支持 SourceMap 符号名恢复，反编译结果接近原始源码的可读性
- 识别 PACKLIST → `[...]`、PACKMAP → `map{...}`、LOGn → `log(...)` 等模式，还原高级语法结构

**优点**：
- 原生可审计性：任何第三方无需依赖开发者提供源码，即可从链上字节码独立还原和验证合约逻辑。这在公链生态中是罕见的特性——对比 Ethereum，用户必须信任开发团队在 Etherscan 上传的"声称匹配"的源码。
- 对大额金融场景，这消除了"闭源合约"的信任黑箱。监管机构、审计师、交易对手方都可以独立验证合约的每一行逻辑。
- 编译管线的双向性保证了 fitsh 语言不是字节码之上的"装饰层"，而是与字节码严格等价的表示——这为形式化验证和自动化审计工具提供了坚实基础。

**局限**：
- 反编译还原的是结构等价的源码，变量名等语义信息依赖 SourceMap 的可用性。若部署时未附带 SourceMap，反编译结果的可读性会有所下降（但逻辑完整性不受影响）。
- 反编译工具链的成熟度和覆盖率需要持续验证，确保所有字节码模式都能被正确还原。

**实际场景**：一个管理 1 亿美元资产的 DeFi 金库合约部署上链后，任何审计师都可以直接从链上字节码反编译出完整的 fitsh 源码，逐行验证资金管理逻辑、权限控制和清算规则。机构投资者在将大额资金存入协议前，可以独立完成合约审计，而不必依赖项目方的"开源承诺"。这对于合规审查和机构级 DeFi 采用而言，是根本性的信任基础设施升级。

### 2.6 Layer 6：合约状态与 DeFi

**机制**：VM 提供完整的状态读写能力：
- `storage_save(key, value)`：持久化存储，按租金模型收费
- `storage_load(key)`：读取存储
- `storage_del(key)`：删除存储
- `storage_rent(key, amount)`：支付存储租金
- `storage_rest(key)`：查询剩余租期

**合约系统特性**：
- 继承链：合约可以声明继承关系，`super.f()` 沿继承链向上查找
- 库引用：通过 `lib` 关键字引用其他合约作为库
- 函数可见性：`public` 函数可被外部调用，私有函数仅限内部
- `callcode`：类似 Solidity 的 `delegatecall`，在当前上下文执行目标代码

**存储租金模型**：
- 存储不是永久免费的，需要按区块高度支付租金
- 过期的存储条目被视为不存在（`sload` 返回空）
- 续租通过 `storage_rent` 支付

**资源限制**：
- `SpaceCap` 定义了栈深度、堆大小、全局变量数量、memory 容量等上限
- 合约加载按字节收取 gas（`contract_load_bytes / 64`）
- 每次新合约加载收取固定 gas（`load_new_contract`）

**优点**：
- 存储租金模型解决了"状态膨胀"问题——这是 Ethereum 至今未解决的核心挑战之一。对于长期运行的 DeFi 协议，这迫使开发者设计更高效的存储方案。
- 合约继承和库系统提供了代码复用能力，减少链上重复部署。
- 资源限制的精细化（栈、堆、全局变量分别限制）比 Ethereum 单一的 gas limit 更能防止特定类型的资源耗尽攻击。

**局限**：
- 存储租金增加了 DeFi 协议的运营复杂度——协议需要持续支付租金或设计用户分摊机制。
- fitsh 语言的生态成熟度远低于 Solidity/Vyper，缺乏成熟的审计工具、形式化验证框架和开发者社区。
- 合约间交互必须通过 AbstCall hook 或 Outer call，没有 Ethereum 中合约可以任意调用任意合约的灵活性。

## 3. 从大额金融结算视角的评估

### 3.1 优势

**可审计性**：Layer 1-2 的声明式设计使得大额交易的资产流向可以在提交前完全审计。这对于机构级结算至关重要——合规团队可以在签名前验证交易的所有可能路径。Layer 5 的 IR 反编译能力进一步将可审计性延伸到合约层——链上部署的任何合约都可以被独立还原为 fitsh 源码进行审查。

**原子性保证**：多方原子交换在 Layer 1 天然支持，无需依赖合约。结合 Layer 2 的条件逻辑，可以构造复杂的条件结算方案（如"如果 A 方资产到位则执行交换，否则退回"）。例如，一笔涉及 HAC、BTC（SAT）、HACD 三种资产的大额 OTC 交易，通过 Layer 1 的原子 AND 组合，要么三种资产同时完成交割，要么全部回滚——不存在"付了 HAC 但没收到 BTC"的中间态。

**攻击面最小化**：
- 资产操作在 protocol 层硬编码，消除了合约级别的转账漏洞
- EXTACTION 限制防止合约代码直接发起资产转移
- AbstCall hook 提供了合约级别的资产流入/流出控制
- Gas 单调消费防止免费试探攻击

**合约透明度**：Layer 5 的 bytecode → fitsh 反编译能力消除了"闭源合约"的信任黑箱。监管机构可直接从链上字节码还原合约逻辑，独立验证资金流向规则是否符合监管要求，无需信任第三方提供的源码。

**状态可控性**：存储租金模型确保链状态不会无限膨胀，这对长期运行的结算系统至关重要。

### 3.2 风险与关注点

**协议层硬编码的双刃剑**：资产操作类型、AbstCall 类型、action 类型都是协议硬编码的。这提供了安全性，但也意味着新功能的引入速度受限于硬分叉周期。对于快速演进的 DeFi 生态，这可能是一个瓶颈。

**VM 安全性的 unsafe 代码**：`setup_vm_run()` 中使用了 raw pointer 来解决 Rust 借用检查的限制。虽然注释详细说明了安全假设（单线程、无并发替换），但这是共识关键路径上的 unsafe 代码，需要格外谨慎。

**全局可变状态**：`ACTION_HOOK_FUNC` 和 `VM_ASSIGN_FUNC` 使用 `static mut` 全局变量，通过 `unsafe` 访问。虽然在单线程共识执行中是安全的，但如果未来引入并行执行，这将成为数据竞争的来源。

**fitsh 语言成熟度**：作为自定义语言，fitsh 缺乏：
- 成熟的形式化验证工具
- 广泛的安全审计经验积累
- 大规模生产环境的验证
这对于承载大额金融资产的 DeFi 协议是一个实质性风险。但 Layer 5 的 IR 反编译能力在一定程度上缓解了这一风险——即使 fitsh 工具链尚不成熟，任何人都可以通过反编译独立验证链上合约的实际行为。

### 3.3 与主流公链的对比定位

| 维度 | Hacash | Ethereum | Bitcoin |
|------|--------|----------|---------|
| 交易级原子组合 | 原生多 action AND 语义 | 单入口点，需合约编排 | UTXO 原子性，无多步组合 |
| 条件逻辑 | AST 层（Layer 2）声明式 | 合约内 if/else | Script 有限条件 |
| 资产操作 | 协议层硬编码 | 合约标准（ERC-20 等） | UTXO 原生 |
| 账户抽象 | 协议原生 | ERC-4337（基础设施层） | 无 |
| 合约透明度 | 原生反编译（Layer 5） | 依赖开发者上传源码 | 无合约 |
| 状态管理 | 租金模型 | 永久存储 | 无状态 |
| 合约灵活性 | AbstCall + Outer call | 任意合约间调用 | 无合约 |
| 可审计性 | 交易体静态可分析 + 合约可反编译 | 需要模拟执行 | UTXO 可追踪 |

---

## 4. 总结

Hacash 的多层可编程性架构是一个经过深思熟虑的设计，它在安全性和灵活性之间做出了明确的取舍：

**核心设计哲学**：将最常用的金融操作（资产转移）固化在协议层，通过分层递进的方式逐步开放更高级的可编程能力。每一层都有明确的能力边界和安全约束。六层架构使得简单结算和复杂 DeFi 各取所需，无需在安全性和灵活性之间做非此即彼的选择。

**最适合的场景**：大额资产结算、多方原子交换、条件支付、需要高可审计性的金融应用。Layer 1-2 的声明式设计在这些场景中具有结构性优势。Layer 5 的 IR 反编译能力为机构级合规审计提供了链上原生支持。

**需要权衡的场景**：高度灵活的 DeFi 协议（如复杂的 AMM、借贷协议）。合约间交互的限制和 AbstCall 的枚举类型约束可能增加开发复杂度。但六层渐进式设计允许简单场景（如代币互换）在 Layer 1-2 完成，仅将真正需要状态管理的复杂逻辑放在 Layer 6。

**关键风险**：fitsh 语言生态的成熟度是当前最大的实质性风险，但 Layer 5 的反编译能力提供了重要的风险缓解——链上合约逻辑始终可被独立验证。协议层硬编码的演进速度是长期需要关注的问题。

从工程实现质量来看，代码库展现了对共识安全性的高度重视——RAII 守卫、gas 单调消费、EXTACTION 限制、状态快照/恢复机制、IR 双向编译保真度等设计都是经过仔细考量的。测试覆盖了多层嵌套、部分提交回滚、深度限制等关键场景。
